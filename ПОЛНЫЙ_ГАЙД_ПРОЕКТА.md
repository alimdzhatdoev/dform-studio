## ЧАСТЬ 1 — КОНЦЕПЦИЯ И ТРЕБОВАНИЯ

### Тема дипломной работы
«Разработка корпоративного сайта с возможностью онлайн-заказов и аналитикой»

### Предметная область
Дизайн-студия DFORM, г. Черкесск. Выбрана как типичный представитель компаний сферы услуг.

### Что система должна делать
1. Публичный сайт — 6 страниц: главная, портфолио, услуги, о студии, заказ, контакты
2. Многошаговая форма онлайн-заказа (4 шага: услуга → описание → бюджет → контакты)
3. Административная панель:
   - Управление заказами (список, статусы, детальное окно)
   - CMS — редактирование всех разделов сайта без разработчика (9 подразделов)
4. Модуль аналитики — сводные показатели, график заказов по дням, распределение по услугам и статусам
5. Аутентификация администратора через логин/пароль с сессиями

### Пользовательские роли
- **Посетитель** — публичная часть + форма заказа
- **Администратор** — полный доступ к админ-панели, CMS, аналитике

## ЧАСТЬ 2 — ТЕХНОЛОГИЧЕСКИЙ СТЕК

### Фронтенд
- **React 19** — функциональные компоненты, хуки, без TypeScript
- **React Router 7** — SPA-маршрутизация
- **Context API** — глобальное состояние (SiteContext для данных сайта)
- **CSS Custom Properties** — дизайн-система через CSS-переменные, без фреймворков
- **Fetch API** — запросы к бэкенду

### Бэкенд
- **Node.js** — встроенный модуль `http`, БЕЗ Express и любых фреймворков
- **REST API** — все эндпоинты вручную: GET/POST/PUT/PATCH/DELETE
- **bcrypt** — хэширование пароля администратора
- **Сессии** — хранятся в памяти процесса, ID передаётся через cookie (HttpOnly, SameSite=Lax)
- **CORS** — настроен вручную для режима разработки (порт 3000 → 8000)

### Хранилище данных
- Физически: **JSON-файлы** в `backend/data/`
- В тексте диплома: описывается как **MySQL** с таблицами и связями
- Структура задокументирована в `schema.sql` (16 таблиц, 5 внешних ключей)

### Инфраструктура
- **Git + GitHub** — репозиторий https://github.com/alimdzhatdoev/dform-studio
- **Render.com** — облачный хостинг, бесплатный тариф
- **Create React App** — сборка фронтенда

## ЧАСТЬ 3 — АРХИТЕКТУРА

### Принцип
Клиент-серверная SPA-архитектура:
```
Браузер (React) → REST API → Node.js сервер → JSON/MySQL хранилище
```

### В режиме разработки
- Фронтенд: `http://localhost:3000` (Create React App dev server)
- Бэкенд: `http://localhost:8000` (Node.js)
- `REACT_APP_API_URL=http://localhost:8000` в `frontend/.env.development`

### В production (Render)
- Один сервис: Node.js строит React-билд и сам его раздаёт
- `NODE_ENV=production` → сервер раздаёт `frontend/build/` как статику
- Все `/api/*` запросы → API-логика
- Все остальные запросы → `index.html` (для SPA-маршрутизатора)
- `REACT_APP_API_URL=''` (пустая строка) — запросы идут на тот же домен

### render.yaml
```yaml
services:
  - type: web
    name: dform-studio
    env: node
    buildCommand: >
      npm install --prefix frontend &&
      npm run build --prefix frontend &&
      npm install --prefix backend
    startCommand: node backend/server.js
    envVars:
      - key: NODE_ENV
        value: production
```

## ЧАСТЬ 5 — КЛЮЧЕВЫЕ ТЕХНИЧЕСКИЕ РЕШЕНИЯ

### useApi хук
```js
// hooks/useApi.js
// Принимает функцию-загрузчик, возвращает { data, loading, error }
// Вызывается при монтировании компонента
```

### SiteContext
- Загружает `/api/site` один раз при старте приложения
- Доступен через `useSite()` во всех компонентах без повторных запросов

### api.js
- Все функции для API в одном месте: `getPortfolio()`, `createOrder()`, `updateOrderStatus()` и т.д.
- Базовый URL из `process.env.REACT_APP_API_URL ?? ''`

### Аутентификация
- POST `/api/auth/login` → проверяет логин/пароль, создаёт сессию, ставит cookie
- GET `/api/auth/check` → проверяет сессию (для автовхода)
- POST `/api/auth/logout` → удаляет сессию, обнуляет cookie через Max-Age=0
- Все защищённые маршруты проверяют сессию через `isAuthenticated()`

### Генерация ID
- `crypto.randomBytes(16).toString('hex')` — строковый ID для заказов, портфолио, услуг
- Числовой автоинкремент — для команды и вспомогательных таблиц

### Аналитика
- Считается из массива заказов при каждом запросе GET `/api/analytics`
- График — последние 30 дней с нулями для дней без заявок
- SVG-график нарисован вручную без библиотек (path, M/L команды)

### ПРАВИЛА СТИЛЯ (критически важно!)

**Запрещено:**
- Маркированные и нумерованные списки — НИКОГДА
- Жирное выделение терминов внутри абзаца — НИКОГДА
- Подзаголовки внутри раздела — НИКОГДА
- Пустые строки между абзацами — НИКОГДА (Word воспринимает их как новые абзацы)

**Обязательно:**
- Стиль: сплошной научный текст, как профессор читает лекцию
- Изложение безличное: «был разработан», «реализована функция», «в ходе анализа установлено»
- Абзацы 6–10 предложений, каждый — одна развёрнутая мысль
- Переходы между абзацами логичные и плавные
- Объём каждого раздела: минимум 5–6 страниц (≈ 4000–5000 слов)

**Правило для задач/перечислений:**
Вместо списка: «Для достижения поставленной цели потребовалось решить ряд задач. На первом этапе был проведён анализ... Далее осуществлялся выбор технологий... После этого...»

### Правило про БД
Физически — JSON-файлы, в тексте диплома описывается как **реляционная база данных MySQL** с таблицами, полями, связями и нормализацией.

### Правило про иллюстрации
- Скриншоты только во второй главе
- Плейсхолдер в тексте: `[Рисунок N — Название]`
- Нумерация сквозная по всей работе
- Перед рисунком обязательна ссылка в тексте

### Список литературы
- Только реально существующие печатные источники
- Интернет-ресурсы не включаются
- Минимум 15 источников
- Формат: `Фамилия И.О. Название. — Город: Издательство, год. — N с.`

## ЧАСТЬ 8 — ПРЕЗЕНТАЦИЯ

### Как генерировалась
Написан Python-скрипт `make_presentation.py` с библиотекой `python-pptx`.
Запуск: `python make_presentation.py` → создаёт `Презентация_DFORM.pptx`

Установка библиотеки: `pip install python-pptx`

### Структура (19 слайдов)
1. Титульный — тема, студент (пустое), руководитель, вуз, год
2. Актуальность — 5 карточек с тезисами
3. Объект / Предмет / Цель — три блока
4. Задачи — 9 пунктов в две колонки с номерами
5. Стек технологий — 4 группы: Фронтенд, Бэкенд, БД, Инфраструктура
6. Архитектура — диаграмма компонентов со стрелками
7. Схема БД — таблицы с полями вертикально (стиль DrawSQL)
8–16. Экранные формы — 9 экранов, каждый: скриншот слева + особенности справа
17. Результаты тестирования — 6 карточек
18. Выводы — 6 пронумерованных пунктов
19. Финальный — «Доклад окончен. Спасибо за внимание!»

### Дизайн-палитра презентации
```python
BG        = RGBColor(0x0C, 0x0C, 0x0E)  # фон
BG_CARD   = RGBColor(0x18, 0x18, 0x1B)  # карточки
BG_CARD2  = RGBColor(0x22, 0x22, 0x26)  # тёмные карточки
ACCENT    = RGBColor(0xE8, 0xF4, 0x39)  # жёлтый акцент
TEXT      = RGBColor(0xF4, 0xEF, 0xE6)  # основной текст
TEXT_MUTED= RGBColor(0x88, 0x85, 0x80)  # приглушённый
```

### Правила дизайна слайдов
- Размер: 16:9, `Inches(13.333) × Inches(7.5)`
- Верхняя и нижняя акцентные полоски на каждом слайде (высота 0.06 дюйма)
- Левая вертикальная полоска на карточках — цвет ACCENT
- Шрифт: Calibri (универсальный, доступен на Windows)
- На слайде с экранной формой: изображение слева (7.6"), особенности справа (4.78")

### Как добавить реальный скриншот в слайд
```python
slide.shapes.add_picture(img_path,
    Inches(x + 0.08), Inches(y + 0.08),
    Inches(w - 0.16), Inches(h - 0.28))
```

### Как извлечь скриншоты из docx
```python
import zipfile, shutil, os
with zipfile.ZipFile('документ.docx', 'r') as z:
    media = [f for f in z.namelist() if f.startswith('word/media/')]
    for m in media:
        z.extract(m, out_dir)
        shutil.move(os.path.join(out_dir, m), os.path.join(out_dir, os.path.basename(m)))
```

### Правила для слайда с БД (таблицы как в DrawSQL)
- Каждая таблица — отдельный прямоугольник
- Заголовок таблицы — отдельный блок сверху, другой цвет фона
- Каждое поле — отдельная строка: `имя поля | тип | флаг (PK/FK/AI)`
- Чередующийся фон строк
- Левая акцентная полоска на каждой таблице

## ЧАСТЬ 9 — РЕЧЬ ДЛЯ ЗАЩИТЫ

### Параметры
- Длительность: 5–6 минут
- Темп: ~120–130 слов в минуту → 600–780 слов

### Формат файла
Markdown-файл `речь_для_защиты.md`:
- Каждый блок начинается с `### [СЛАЙД N — Название]`
- После заголовка — текст для произнесения
- В конце — таблица с хронометражом по слайдам
- В конце — советы (не торопиться, показывать рукой на экран и т.д.)

### Принципы речи
- На слайды 8–16 (экранные формы) не тратить по 30+ секунд на каждый — группировать по смыслу
- На сложных слайдах (БД, архитектура) можно сказать: «подробно описано в работе»
- Выводы произносить уверенно и чётко — это последнее что запомнит комиссия

### Хронометраж (шаблон)

## ЧАСТЬ 13 — ВАЖНЫЕ МЕЛОЧИ И ПОДВОДНЫЕ КАМНИ

### Git
- Если вложенная `.git` папка (create-react-app создаёт свою): `git rm --cached -f frontend && rm -rf frontend/.git`
- Если remote опережает: `git pull origin main --no-rebase -X ours` → push

### Node.js сервер
- Порт: `process.env.PORT || 8000` — Render сам задаёт PORT
- Logout cookie: обязательно `Max-Age=0` чтобы браузер удалил cookie
- CORS: в dev нужен `Access-Control-Allow-Credentials: true` для cookies

### Презентация
- ФИО студента оставляется пустым (по договорённости с заказчиком)
- В стеке: писать MySQL, не JSON
- Таблицы БД: поля вертикально, не в строку

### Текст диплома
- Между абзацами НЕТ пустых строк (иначе Word считает их отдельными абзацами)
- Объём мал → комиссия снижает оценку → минимум 5 страниц на раздел
- Слова-маркеры которые нельзя использовать: «во-первых», «во-вторых» как начало абзаца с двоеточием

### Render (бесплатный тариф)
- Сервис «засыпает» через 15 минут без запросов → первый запрос ~10-15 сек
- JSON-файлы на Render эфемерны — при рестарте могут сброситься
- Для production нужна реальная БД (Render PostgreSQL или внешняя MySQL)
