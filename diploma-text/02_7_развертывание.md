## 2.7. Развёртывание приложения

Развёртывание приложения на публично доступной облачной платформе является завершающим этапом практической разработки и преследует несколько целей: обеспечение доступности системы для реальных пользователей, проверку корректности работы приложения в производственной среде, отличающейся от локальной среды разработки, а также демонстрацию практической применимости разработанного решения. В данном разделе описываются подготовительные меры, предпринятые для адаптации приложения к производственному режиму, конфигурация развёртывания на платформе Render, процесс сборки и запуска сервиса, а также особенности производственной конфигурации по сравнению с режимом разработки.
Выбор платформы Render в качестве провайдера облачного хостинга обусловлен рядом факторов. Render предоставляет бесплатный тариф для Node.js-приложений, достаточный для демонстрационного использования в рамках учебного проекта. Платформа поддерживает автоматическое развёртывание (Continuous Deployment) из репозиториев GitHub: при каждом обновлении указанной ветки репозитория Render автоматически выполняет сборку и перезапуск сервиса с новой версией кода. Это означает, что для обновления развёрнутого приложения достаточно выполнить git push — никаких дополнительных действий по развёртыванию не требуется. Render поддерживает конфигурирование сервисов через файл render.yaml в корне репозитория, что обеспечивает декларативное описание параметров развёртывания и хранение конфигурации вместе с кодом проекта.
Файл render.yaml содержит описание единственного сервиса типа web с именем dform-studio. Тип сервиса web означает, что Render обеспечивает публичный HTTP-доступ к сервису через автоматически назначаемый поддомен вида *.onrender.com. В разделе buildCommand указана последовательность команд, выполняемых при каждом развёртывании: установка зависимостей фронтенда, сборка React-приложения в производственную директорию build и установка зависимостей бэкенда. В разделе startCommand указана команда запуска: node backend/server.js — простой запуск серверного файла без использования менеджеров процессов. В секции envVars задаётся переменная окружения NODE_ENV со значением production, что активирует в серверном коде режим раздачи статических файлов. Платформа Render самостоятельно назначает переменную PORT и передаёт её серверному процессу.
Для корректной работы одностраничного React-приложения в производственном режиме потребовалась дополнительная настройка серверного кода. Проблема заключается в следующем: SPA-приложение управляет маршрутизацией средствами JavaScript на стороне клиента, однако при прямом переходе по адресу вида https://dform-studio.onrender.com/portfolio/some-id браузер отправляет HTTP-запрос к серверу с этим URL. Если сервер не знает о маршруте /portfolio/some-id, он вернёт ошибку 404. Решение состоит в настройке сервера таким образом, чтобы любой запрос, не являющийся API-вызовом и не соответствующий существующему статическому файлу, возвращал файл index.html. Получив этот файл, браузер загрузит JavaScript-код приложения, который разберёт текущий URL и отобразит соответствующий компонент страницы. Эта логика реализована в функции serveStatic серверного кода: при отсутствии запрашиваемого файла в директории build осуществляется отдача index.html как fallback-ответа.
В производственной среде фронтенд-приложение собирается командой npm run build, которая активирует производственную сборку Create React App. В ходе этой сборки Webpack выполняет минификацию JavaScript и CSS, разбиение кода на чанки для параллельной загрузки, добавление хэша к именам файлов для управления кэшированием, а также оптимизацию импортов. Производственная сборка по объёму значительно меньше кода разработки: весь пользовательский код фронтенда компилируется в несколько файлов с минифицированным кодом и удалёнными отладочными сообщениями. В переменной окружения REACT_APP_API_URL для производственной среды указывается пустая строка, что означает обращение к тому же домену — поскольку и фронтенд, и API обслуживаются одним Node.js-сервером, никакого кросс-доменного взаимодействия в производственной среде не возникает.
Репозиторий проекта размещён на платформе GitHub по адресу https://github.com/alimdzhatdoev/dform-studio. Структура репозитория включает директории frontend (фронтенд React-приложения) и backend (серверная часть), а также файлы render.yaml и schema.sql в корневой директории. При регистрации сервиса на Render был указан данный репозиторий и ветка main в качестве источника кода. Сервис связан с GitHub через OAuth-интеграцию, что обеспечивает автоматическое получение уведомлений о новых коммитах в ветку main и запуск процесса пересборки при каждом обновлении. Полный процесс сборки — установка зависимостей, компиляция React-приложения и установка зависимостей бэкенда — занимает в среднем две-три минуты, после чего новая версия приложения становится доступной по публичному адресу.
Развёрнутое приложение доступно по публичному URL, автоматически назначенному платформой Render. Функциональность развёрнутого приложения полностью соответствует функциональности, проверенной в ходе тестирования: все страницы публичного сайта отображаются корректно, форма заказа принимает и сохраняет заявки, административная панель доступна по защищённому маршруту и предоставляет полный набор инструментов управления контентом. Следует рассмотреть особенности производственной среды, оказывающие влияние на поведение приложения. На бесплатном тарифе Render сервис переходит в режим гибернации после пятнадцати минут отсутствия запросов, что приводит к задержке первого обращения — сервер «просыпается» и отвечает на первый запрос с задержкой около десяти-пятнадцати секунд. Это является ограничением бесплатного тарифа и не является дефектом приложения; при использовании платного тарифа сервис работает непрерывно без задержек. Хранение данных в JSON-файлах на файловой системе контейнера Render предполагает эфемерность данных: при перезапуске или пересборке сервиса данные JSON-файлов могут быть сброшены. Это является известным ограничением при использовании файловой системы контейнера для хранения данных; для сохранения данных между перезапусками следует использовать постоянные диски (persistent disks) или внешнюю базу данных. В контексте учебного проекта данное ограничение не является критическим и принимается как допустимое.
Безопасность производственной среды обеспечивается несколькими мерами. Платформа Render автоматически настраивает HTTPS: все запросы к сервису шифруются протоколом TLS/SSL, что защищает передаваемые данные, включая учётные данные при входе в административную панель. Административные API-маршруты защищены серверной проверкой сессии. Cookie с идентификатором сессии передаётся с атрибутами HttpOnly и SameSite=Lax, что ограничивает возможности его перехвата через JavaScript или кросс-сайтовые запросы. Пароль администратора хранится в хэшированном виде с использованием bcrypt, что исключает его восстановление даже при получении несанкционированного доступа к файлу конфигурации. В целом реализованные меры безопасности соответствуют стандартам, принятым для веб-приложений данного класса. Успешное развёртывание приложения на публичной облачной платформе завершает практическую часть работы и подтверждает готовность системы к реальной эксплуатации.
