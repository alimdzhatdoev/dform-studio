## 1.6. Проектирование архитектуры приложения

Архитектура программного обеспечения — это совокупность фундаментальных решений о структуре системы, определяющих её разбиение на компоненты, принципы взаимодействия между ними и распределение ответственности между частями системы. Проектирование архитектуры предшествует реализации и обеспечивает согласованность всех принимаемых в ходе разработки решений с общей концепцией системы. Грамотно спроектированная архитектура снижает сложность системы за счёт разделения обязанностей, упрощает тестирование отдельных компонентов, создаёт предпосылки для масштабирования и облегчает внесение изменений без необходимости переработки всей системы. В данном разделе описываются ключевые архитектурные решения, принятые при проектировании разрабатываемого корпоративного сайта: общая схема взаимодействия клиента и сервера, организация серверной части, структура клиентского приложения, принципы управления состоянием и организация взаимодействия компонентов через API.
Разрабатываемая система построена на основе клиент-серверной архитектуры, при которой клиентская часть (фронтенд) и серверная часть (бэкенд) представляют собой логически независимые компоненты, взаимодействующие посредством стандартизированного программного интерфейса. Такая архитектура противопоставляется монолитному подходу, при котором генерация HTML-разметки происходит на сервере и результат передаётся клиенту в виде готовой страницы. Разделение фронтенда и бэкенда в данном проекте обусловлено рядом преимуществ: оно позволяет разрабатывать оба компонента независимо, используя оптимальные для каждого из них инструменты; обеспечивает возможность повторного использования API-интерфейса для потенциальных будущих клиентов (мобильного приложения или другого фронтенда); а также создаёт более богатый пользовательский опыт за счёт мгновенных переходов между страницами без полной перезагрузки браузера.
Серверная часть системы реализована в виде HTTP-сервера на платформе Node.js, обеспечивающего два класса функций. Первая функция — предоставление REST API для взаимодействия с клиентским приложением. REST (Representational State Transfer) — это архитектурный стиль проектирования распределённых систем, ориентированный на операции с ресурсами через стандартные HTTP-методы. В рамках REST каждый ресурс идентифицируется уникальным URL, а тип выполняемой операции определяется HTTP-методом: GET используется для получения данных, POST — для создания новых ресурсов, PUT или PATCH — для обновления существующих, DELETE — для удаления. Сервер возвращает данные в формате JSON — стандартном для веб-API текстовом формате, нативно поддерживаемом JavaScript. Вторая функция сервера — раздача статических файлов клиентского приложения в производственной среде. При развёртывании на Render Node.js-сервер обслуживает файлы скомпилированного React-приложения из директории frontend/build и направляет все запросы к не-API маршрутам на главный файл index.html, что обеспечивает корректную работу клиентского маршрутизатора.
Структура API разделена на логические группы маршрутов в соответствии с предметными областями. Публичные маршруты — доступные без аутентификации — включают получение списков и детальной информации для всех разделов публичного сайта: портфолио, услуги, команда, настройки сайта, контакты, а также создание новой заявки через форму заказа. Защищённые маршруты — доступные только авторизованным пользователям — включают все операции управления данными: создание, обновление и удаление элементов портфолио, услуг, команды и настроек сайта, а также просмотр и изменение статусов заказов и получение аналитических данных. Аутентификационные маршруты обеспечивают вход в систему и выход из неё. Каждый маршрут реализован как обработчик, проверяющий метод и URL запроса, извлекающий параметры, выполняющий необходимые операции с файловым хранилищем и возвращающий ответ в формате JSON с соответствующим HTTP-статус-кодом.
Клиентская часть приложения реализована как одностраничное приложение (SPA) на основе React. При первом обращении к сайту браузер загружает единственный HTML-документ и скомпилированный JavaScript-бандл, содержащий весь код приложения. Все последующие переходы между страницами выполняются посредством клиентской маршрутизации: React Router перехватывает навигационные события браузера и обновляет отображаемый компонент в соответствии с текущим URL, не инициируя обращений к серверу. Фактически загрузка данных происходит по требованию — при монтировании компонента страницы выполняется запрос к соответствующему API-эндпоинту, данные сохраняются в локальном состоянии компонента и используются для рендеринга. Такой подход обеспечивает быстрый отклик интерфейса после первоначальной загрузки, поскольку навигация не требует ожидания ответа от сервера.
Организационная структура клиентского приложения следует принятым в экосистеме React конвенциям. Директория src содержит все исходные файлы приложения, разделённые по функциональному назначению. Директория pages содержит компоненты верхнего уровня, соответствующие страницам приложения — Home, Portfolio, Services, About, Order, Contacts и Admin. Директория components содержит переиспользуемые компоненты, применяемые на нескольких страницах: шапку и подвал сайта, карточки проектов и услуг, компоненты форм и прочие UI-элементы. Директория hooks содержит кастомные хуки, инкапсулирующие логику получения данных с сервера: хук useApi принимает функцию-загрузчик данных и возвращает объект с текущим состоянием запроса — данными, флагом загрузки и информацией об ошибке. Директория utils содержит вспомогательные функции, в том числе модуль api.js с набором функций для выполнения запросов к каждому эндпоинту сервера. Директория context содержит контексты React для распределения глобального состояния.
Управление состоянием приложения организовано на нескольких уровнях. На уровне отдельного компонента используется хук useState для хранения локального состояния, например текущего активного шага формы заказа или выбранного фильтра в портфолио. На уровне страницы компонент-страница загружает данные с сервера и передаёт их дочерним компонентам через свойства. На уровне приложения используется Context API для состояния, необходимого нескольким страницам одновременно. Конкретным примером глобального контекста является SiteContext, предоставляющий данные о настройках сайта — тексты главного экрана, история студии, настройки CTA-блока и футера — всем компонентам, которые в них нуждаются. Эти данные загружаются один раз при инициализации приложения и доступны через хук useSite() без повторных запросов к API. Данный подход устраняет избыточные сетевые запросы и обеспечивает согласованность отображаемых данных на всех страницах.
Административная панель реализована как отдельная страница приложения (компонент Admin), доступная по маршруту /admin. Маршрут защищён проверкой аутентификации: при загрузке компонента выполняется запрос к API-эндпоинту проверки сессии, и если пользователь не авторизован, выполняется перенаправление на страницу входа. После успешной аутентификации отображается интерфейс административной панели с вкладочной навигацией по разделам: аналитика, заказы, портфолио, услуги, команда и настройки сайта. Каждый раздел реализован как самостоятельный компонент-вкладка, загружающий необходимые данные при монтировании и предоставляющий интерфейс для их редактирования. Структура форм редактирования соответствует структуре таблиц базы данных: каждое поле таблицы имеет соответствующий элемент ввода в форме. Операции сохранения данных выполняются через API с оптимистичным обновлением интерфейса — изменения отражаются в UI немедленно, а при ошибке API состояние откатывается к предыдущему.
Взаимодействие между фронтендом и бэкендом построено на принципе единственного источника истины: фронтенд не хранит постоянных данных и при каждом монтировании компонента загружает актуальную информацию с сервера. Это означает, что данные всегда актуальны, а кэширование на стороне клиента не порождает рассогласования с реальным состоянием хранилища. Все запросы к API выполняются через централизованный модуль api.js, инкапсулирующий детали HTTP-взаимодействия: формирование URL, установку заголовков, сериализацию тела запроса и разбор ответа. Это позволяет при необходимости изменить базовый URL API или добавить общую обработку ошибок в одном месте без затрагивания компонентов. Переменная окружения REACT_APP_API_URL позволяет задать базовый URL для API: в среде разработки она указывает на локальный сервер Node.js, а в производственной среде остаётся пустой строкой, что означает обращение к тому же домену, с которого обслуживается статика.
Отдельного рассмотрения заслуживает архитектура производственного развёртывания, при которой Node.js-сервер выполняет двойную роль: он одновременно обслуживает API-запросы и раздаёт статические файлы React-приложения. При запуске в режиме production сервер определяет это через переменную окружения NODE_ENV и активирует логику обслуживания статики из директории frontend/build. Запросы к маршрутам, начинающимся с /api, обрабатываются как API-вызовы, а все прочие запросы возвращают файл index.html — точку входа в SPA. Такой подход позволяет развернуть всё приложение как единый сервис без необходимости настройки отдельного статического хостинга для фронтенда и отдельного API-сервера для бэкенда, что существенно упрощает конфигурацию развёртывания и снижает операционные расходы. Описанная архитектура создаёт прочный фундамент для практической реализации всех компонентов системы, которая подробно рассматривается во второй главе настоящей работы.
