## 1.5. Проектирование структуры базы данных

Проектирование структуры базы данных является важнейшим этапом разработки любой информационной системы, работающей с постоянно хранимыми данными. Грамотно спроектированная схема данных обеспечивает целостность и непротиворечивость хранимой информации, исключает избыточное дублирование данных, создаёт основу для эффективного выполнения запросов и упрощает расширение системы в будущем. В контексте данной работы, несмотря на то что в качестве физического механизма хранения данных используются JSON-файлы на файловой системе сервера, проектирование логической структуры базы данных выполнено в терминах реляционной модели с использованием MySQL. Такой подход позволяет чётко определить сущности системы, их атрибуты и связи между ними, а также обеспечить возможность миграции на полноценную СУБД при масштабировании системы без изменения логики приложения. Разработанная схема реализована в виде SQL-файла и содержит определения всех таблиц с указанием типов данных, ограничений целостности и внешних ключей.
При проектировании схемы базы данных применяется методология «сущность — атрибут — связь», в рамках которой сначала выявляются все объекты предметной области, требующие хранения информации, затем для каждого объекта определяется набор характеристик, а после этого устанавливаются типы и направления связей между сущностями. В данной системе выделено шестнадцать таблиц, которые можно разделить на несколько смысловых групп: таблицы для хранения бизнес-данных (заказы, услуги, портфолио), таблицы для хранения содержимого публичного сайта (команда, настройки разделов), таблицы для хранения аналитических данных и вспомогательные таблицы. Рассмотрение структуры каждой таблицы позволит не только описать модель данных, но и прояснить логику работы соответствующих функциональных блоков системы.
Центральной сущностью бизнес-логики системы является таблица orders — хранилище всех поступивших заявок. Каждая запись в этой таблице соответствует одной заявке клиента и содержит следующие атрибуты: уникальный строковый идентификатор (поле id типа VARCHAR(64)), генерируемый сервером при создании заявки; имя клиента (поле name типа VARCHAR(255)); адрес электронной почты (поле email типа VARCHAR(255)); номер телефона (поле phone типа VARCHAR(50), допускающее значение NULL, поскольку телефон является необязательным полем формы); идентификатор выбранной услуги (поле service_id типа VARCHAR(64), являющееся внешним ключом к таблице услуг); развёрнутое описание задачи клиента (поле description типа TEXT); предполагаемый бюджет (поле budget типа VARCHAR(100), допускающее NULL); текущий статус заявки (поле status типа ENUM с допустимыми значениями 'new', 'in_progress', 'completed', 'cancelled', по умолчанию 'new'); дата и время создания заявки (поле created_at типа DATETIME); а также дата и время последнего обновления (поле updated_at типа DATETIME, допускающее NULL). Использование строкового идентификатора вместо автоинкрементного целого числа обусловлено тем, что генерация ID на стороне сервера без обращения к базе данных упрощает логику создания записей при использовании JSON-хранилища. Статус заявки ограничен перечислением возможных значений с помощью типа ENUM, что обеспечивает целостность данных и исключает сохранение некорректных состояний.
Таблица services содержит описание услуг, предлагаемых студией, и связана с таблицей заказов через внешний ключ. Каждая запись включает идентификатор услуги (поле id типа VARCHAR(64)), эмодзи-иконку для визуального обозначения (поле icon), наименование услуги (поле title), описание (поле description типа TEXT), ценовой ориентир (поле price типа VARCHAR(100)) и ориентировочный срок выполнения (поле duration типа VARCHAR(100)). Использование строковых типов для цены и длительности вместо числовых значений обусловлено тем, что эти параметры нередко представляются в виде диапазонов или сопровождаются текстовыми пометками, например «от 30 000 руб.» или «2–4 недели». Детализированный перечень работ, входящих в услугу, хранится в отдельной таблице service_features, которая реализует связь «один ко многим» с таблицей services. Каждая запись в service_features содержит идентификатор родительской услуги (service_id с каскадным удалением при удалении услуги), текст конкретного пункта перечня (поле feature) и порядковый номер для упорядочивания при отображении (поле sort_order). Вынесение списка характеристик в отдельную таблицу вместо хранения в виде строки с разделителями соответствует требованиям первой нормальной формы реляционной модели и упрощает добавление и удаление отдельных пунктов без редактирования агрегированной строки.
Таблица portfolio предназначена для хранения записей о выполненных проектах, демонстрируемых в соответствующем разделе сайта. Структура таблицы включает идентификатор проекта (поле id типа VARCHAR(64)), его наименование (поле title), категорию — например, «Брендинг», «Веб-дизайн», «Иллюстрация» — (поле category типа VARCHAR(100)), название клиента (поле client), год выполнения (поле year типа VARCHAR(10)), текстовое описание проекта (поле description типа TEXT), акцентный цвет карточки проекта в шестнадцатеричном формате (поле color), а также три статистических показателя проекта: продолжительность (поле stats_duration), объём поставляемых материалов (поле stats_deliverables) и достигнутый результат (поле stats_result). Теги проекта, как и характеристики услуг, вынесены в отдельную таблицу portfolio_tags со связью «один ко многим», содержащую идентификатор родительского проекта, текст тега и порядковый номер. Такая структура обеспечивает гибкость в управлении тегами и позволяет в будущем реализовать фильтрацию проектов по тегам без изменения схемы.
Для хранения информации о членах команды студии предназначена таблица team. Каждая запись содержит автоинкрементный числовой идентификатор (поле id), имя сотрудника (поле name), его должность или роль (поле role), биографическую справку (поле bio типа TEXT), инициалы для аватара-заполнителя (поле initials типа VARCHAR(5)) и акцентный цвет аватара (поле color). Применение инициалов вместо фотографии является осознанным дизайнерским решением: оно обеспечивает единообразное отображение карточек команды независимо от наличия фотографий и соответствует минималистичной эстетике студии. Числовой автоинкрементный идентификатор используется в таблице team вместо строкового, поскольку управление записями о сотрудниках не требует клиентской генерации ID.
Таблицы, хранящие содержимое публичного сайта, сгруппированы по разделам. Таблица site_hero содержит настройки главного экрана (hero-секции) сайта: метку-тег над заголовком (поле label), несколько строк заголовка с выделенным акцентным словом (поля title_line1, title_accent, title_line2, title_line3) и описание (поле description). Использование нескольких полей для заголовка вместо единой строки обусловлено необходимостью точного управления переносами строк и выделением акцентного слова разным цветом — чего невозможно добиться при хранении заголовка как единого текстового значения. Таблица site_about хранит настройки раздела «О студии» — заголовок — и связана с таблицей site_about_paragraphs, содержащей отдельные абзацы текста истории студии с порядковым номером для управления их последовательностью. Таблица site_cta содержит настройки блока призыва к действию: тег, заголовок и описание. Таблица site_footer хранит слоган в подвале сайта и строку копирайта. Все перечисленные таблицы имеют фиксированный первичный ключ, равный единице (DEFAULT 1), поскольку каждая из них содержит ровно одну запись — singleton-запись с настройками соответствующего раздела.
Вспомогательные таблицы обеспечивают хранение дополнительных элементов публичного сайта. Таблица clients содержит перечень клиентов студии с их наименованиями и служит источником данных для соответствующего блока на странице «О студии». Таблица stats хранит числовые показатели компании, отображаемые в виде блока статистики, — каждая запись содержит значение показателя (например, «150+») и его текстовую метку (например, «реализованных проектов»). Таблица company_values предназначена для хранения ценностей компании: каждая запись включает иконку, заголовок ценности и её описание. Таблица contacts содержит контактную информацию — каждый контактный пункт (адрес, телефон, электронная почта) хранится отдельной записью с иконкой, меткой и значением. Таблица social_links предназначена для хранения ссылок на страницы компании в социальных сетях с указанием названия платформы и URL.
Таблицы аналитических данных имеют структуру, отражающую требования к модулю аналитики, описанные в разделе 1.3. Таблица analytics содержит агрегированные показатели: общее количество заказов (поле total_orders) и общую сумму заказов (поле total_revenue). Таблица analytics_orders_by_day хранит детализированные данные о динамике заказов в разбивке по дням: каждая запись связана с родительской записью в таблице analytics (поле analytics_id с внешним ключом) и содержит дату (поле date типа DATE) и количество заказов за этот день (поле count). Уникальный индекс на поле date (UNIQUE KEY uq_date) гарантирует, что для каждой календарной даты существует не более одной записи. Следует отметить, что в производственной реализации аналитические данные для графика вычисляются непосредственно из таблицы orders при каждом запросе к аналитическому эндпоинту, а таблица analytics_orders_by_day представляет собой проектное решение для потенциальной оптимизации через кэширование агрегатов.
Между таблицами установлены следующие связи через внешние ключи. Таблица service_features ссылается на таблицу services через поле service_id с каскадным удалением, что означает автоматическое удаление всех характеристик услуги при удалении самой услуги — это обеспечивает целостность данных и предотвращает накопление «осиротевших» записей. Таблица orders ссылается на таблицу services через поле service_id, устанавливая связь «заказ содержит ссылку на услугу»; данная связь не предполагает каскадного удаления, поскольку удаление услуги не должно уничтожать историю связанных с ней заказов. Таблица analytics_orders_by_day ссылается на таблицу analytics через поле analytics_id с каскадным удалением. Таблица portfolio_tags ссылается на таблицу portfolio через поле portfolio_id с каскадным удалением. Таблица site_about_paragraphs ссылается на таблицу site_about через поле about_id с каскадным удалением.
Разработанная схема придерживается принципов нормализации данных до третьей нормальной формы: каждая таблица хранит данные об одной сущности, все атрибуты зависят только от первичного ключа, а не от других не-ключевых атрибутов. Вынесение списочных атрибутов (характеристики услуг, теги проектов, абзацы текста) в отдельные связанные таблицы соответствует требованиям первой нормальной формы об атомарности значений. Нормализованная структура обеспечивает отсутствие аномалий при обновлении, вставке и удалении данных, что является критически важным для системы, предполагающей регулярную модификацию контента через административную панель. Таким образом, спроектированная база данных обеспечивает надёжное и структурированное хранение всей информации, необходимой для работы разрабатываемой системы, и служит основой для реализации API-эндпоинтов, описанных в разделе 2.1 второй главы.
