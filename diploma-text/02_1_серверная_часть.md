## 2.1. Реализация серверной части приложения

Вторая глава дипломной работы посвящена практической реализации всех компонентов разработанной системы. В отличие от первой главы, где рассматривались теоретические основы, анализ предметной области и проектные решения, вторая глава описывает конкретные технические решения, применённые при написании кода, и результаты их реализации. Изложение построено в соответствии с логической последовательностью разработки: от серверной части и API, обеспечивающих основу работы всей системы, к клиентскому интерфейсу, отдельным функциональным модулям и, наконец, к тестированию и развёртыванию. В данном разделе рассматривается реализация серверной части приложения — HTTP-сервера на платформе Node.js, организации файлового хранилища, структуры REST API и механизмов аутентификации.
Серверная часть приложения реализована в виде единого файла server.js в директории backend, что отражает принципиальное решение об отказе от использования фреймворков. Точкой входа является создание HTTP-сервера средствами встроенного модуля http платформы Node.js: функция createServer принимает обработчик запросов и возвращает объект сервера, который запускается на указанном порту. Порт определяется из переменной окружения PORT, что является стандартной практикой для облачных платформ, самостоятельно назначающих порт при развёртывании; при отсутствии переменной используется значение по умолчанию 8000 для локальной разработки. Переменная окружения NODE_ENV используется для определения режима работы: при значении 'production' активируется логика раздачи статических файлов скомпилированного React-приложения.
Каждый входящий HTTP-запрос проходит через централизованный обработчик, реализующий маршрутизацию. Обработчик разбирает URL запроса с помощью встроенного класса URL, извлекает путь и строку запроса, определяет HTTP-метод и на основании этих данных принимает решение о том, какой обработчик должен обслужить запрос. Для API-запросов (маршруты, начинающиеся с префикса /api/) выполняется чтение тела запроса — если оно присутствует — посредством накопления чанков данных из потока запроса, после чего разобранный JSON-объект передаётся в соответствующий обработчик. Для запросов к статическим файлам (в производственном режиме) используется вспомогательная функция serveStatic, определяющая путь к файлу относительно директории frontend/build и отдающая его содержимое с корректным заголовком Content-Type. Все запросы к несуществующим маршрутам, не являющиеся API-запросами, перенаправляются на index.html — это обеспечивает корректную работу клиентского маршрутизатора при обновлении страницы или прямом переходе по URL.
Установка заголовков CORS (Cross-Origin Resource Sharing) является необходимой мерой при клиент-серверной архитектуре с разделением портов в режиме разработки. Поскольку в процессе разработки фронтенд-приложение обслуживается сервером Create React App на порту 3000, а API-сервер работает на порту 8000, браузер расценивает запросы к API как межсайтовые и блокирует их по умолчанию. Для решения этой проблемы сервер устанавливает заголовок Access-Control-Allow-Origin, разрешающий запросы с адреса фронтенд-сервера разработки, а также заголовки Access-Control-Allow-Methods и Access-Control-Allow-Headers, перечисляющие разрешённые методы и заголовки. Заголовок Access-Control-Allow-Credentials: true необходим для корректной передачи cookies сессии в кросс-доменных запросах. Предполётные OPTIONS-запросы, автоматически отправляемые браузером перед кросс-доменными запросами с нестандартными методами, обрабатываются отдельно и возвращают статус 204 без тела ответа.
Механизм аутентификации реализован на основе серверных сессий с хранением идентификатора сессии в cookie. При успешном входе администратора — после проверки введённых учётных данных против сохранённых в конфигурационном файле — сервер генерирует уникальный идентификатор сессии средствами встроенного модуля crypto (функция randomBytes, возвращающая случайную последовательность байт в шестнадцатеричном представлении) и сохраняет его в словаре sessions, ключом в котором служит идентификатор, а значением — объект с данными сессии и временной меткой создания. Идентификатор сессии передаётся клиенту в виде cookie через заголовок Set-Cookie с атрибутами HttpOnly (запрещает доступ к cookie из JavaScript, защищая от XSS-атак), SameSite=Lax (ограничивает отправку cookie в кросс-сайтовых запросах) и Path=/ (делает cookie доступным для всех маршрутов). Пароль администратора хранится в хэшированном виде с применением алгоритма bcrypt: при проверке введённого пароля используется функция bcrypt.compare, обеспечивающая безопасное сравнение без риска атак по времени выполнения.
При каждом запросе к защищённым маршрутам выполняется проверка сессии: из cookie запроса извлекается идентификатор, и если соответствующая запись найдена в словаре sessions и не истекла по времени жизни, запрос считается авторизованным. Функция-помощник isAuthenticated инкапсулирует эту логику и вызывается в начале обработки каждого защищённого маршрута, возвращая управление с ответом 401 (Unauthorized) при отсутствии действующей сессии. При выходе из системы сервер удаляет запись из словаря sessions и возвращает клиенту cookie с истёкшим сроком действия через заголовок Set-Cookie с атрибутом Max-Age=0, что принудительно удаляет cookie в браузере. Такой механизм обеспечивает корректную инвалидацию сессии как на стороне сервера, так и на стороне клиента.
Файловое хранилище данных организовано в директории backend/data, содержащей JSON-файлы для каждой сущности системы. Операции чтения и записи данных реализованы через два вспомогательных метода: readData(filename) читает указанный файл и возвращает разобранный JSON-массив объектов, а writeData(filename, data) сериализует переданный массив объектов в JSON и записывает его в файл с форматированием (два пробела в качестве отступа для читаемости). Оба метода работают синхронно с использованием функций fs.readFileSync и fs.writeFileSync, что упрощает код обработчиков и является приемлемым решением для сервера с небольшой нагрузкой. При операциях чтения реализована обработка ошибки ENOENT — если файл хранилища ещё не существует, метод readData возвращает пустой массив вместо генерации исключения.
Структура API-эндпоинтов строго следует принципам REST. Эндпоинт GET /api/portfolio возвращает массив всех проектов портфолио; GET /api/portfolio/:id возвращает детальные данные конкретного проекта по его идентификатору; POST /api/portfolio (защищённый) создаёт новый проект; PUT /api/portfolio/:id (защищённый) обновляет существующий проект; DELETE /api/portfolio/:id (защищённый) удаляет проект. Аналогичная структура применяется для услуг (маршруты /api/services), команды (/api/team), заказов (/api/orders) и настроек сайта (/api/site). Специфическим является эндпоинт PATCH /api/orders/:id/status, принимающий только новое значение статуса заказа без замены всей записи — это соответствует принципу минимального обновления и снижает риск случайной перезаписи данных. Эндпоинт GET /api/analytics возвращает агрегированные данные, вычисляемые на лету из массива заказов: общее количество заявок, распределение по статусам, распределение по услугам и динамику поступления по дням за последние тридцать дней.
Обработка ошибок в серверном коде реализована на нескольких уровнях. На уровне обработчика запросов каждый маршрут обёрнут в блок try-catch, перехватывающий исключения и возвращающий ответ с кодом 500 (Internal Server Error) и описанием ошибки. На уровне валидации входных данных для операций создания и обновления проверяется наличие обязательных полей, и при их отсутствии возвращается код 400 (Bad Request) с указанием недостающих полей. При обращении к несуществующему ресурсу — например, при попытке получить проект портфолио с несуществующим ID — возвращается код 404 (Not Found). Все ответы API имеют единообразную структуру: для успешных операций возвращается запрошенный ресурс или объект с подтверждением успеха, для ошибочных — объект с полем error, содержащим текстовое описание ошибки. Такое единообразие упрощает обработку ответов на стороне клиента.

В производственной конфигурации, описанной в разделе 2.7, Node.js-сервер дополнительно выполняет функцию раздачи статических файлов скомпилированного React-приложения. При старте в режиме production сервер определяет абсолютный путь к директории frontend/build и инициализирует карту MIME-типов для корректной установки заголовка Content-Type при отдаче файлов различных форматов — HTML, CSS, JavaScript, изображений и шрифтов. При получении запроса к статическому файлу сервер формирует полный путь к файлу, проверяет его существование и отдаёт содержимое с соответствующим заголовком. Запросы к несуществующим статическим файлам, не являющиеся API-вызовами, возвращают файл index.html — это ключевой механизм, обеспечивающий корректную работу SPA-маршрутизации при прямых переходах по URL. Реализованная серверная часть обеспечивает полный набор функций, необходимых для работы всей системы, и служит основой для функционирования клиентского приложения, описанного в следующем разделе.
