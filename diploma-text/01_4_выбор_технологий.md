## 1.4. Выбор и обоснование технологического стека

Выбор технологического стека является одним из ключевых архитектурных решений в процессе разработки веб-приложения, поскольку определяет не только технические возможности системы, но и удобство её разработки, производительность в эксплуатации, доступность документации и экосистемы, а также перспективы долгосрочного сопровождения. Решение о выборе конкретных технологий принимается с учётом нескольких факторов: соответствия инструментов функциональным требованиям к системе, зрелости и стабильности технологии, размера сообщества и качества документации, а также практического опыта разработчика, позволяющего реализовать задачу в разумные сроки. В данном разделе обосновывается выбор каждого компонента технологического стека разрабатываемой системы — библиотеки для построения пользовательского интерфейса, серверной среды выполнения, механизма хранения данных, инструментов сборки и развёртывания.
Для реализации клиентской части приложения была выбрана библиотека React версии 19, разработанная компанией Meta и являющаяся одной из наиболее распространённых технологий построения пользовательских интерфейсов в современной веб-разработке. React основан на концепции компонентного подхода: интерфейс представляется как дерево независимых переиспользуемых компонентов, каждый из которых отвечает за отображение конкретного фрагмента UI и управление связанным с ним состоянием. Ключевым преимуществом React является декларативная модель программирования: разработчик описывает, как должен выглядеть интерфейс в зависимости от текущего состояния приложения, а библиотека самостоятельно определяет минимальный набор изменений, необходимых для обновления реального DOM-дерева. Этот механизм, реализованный через виртуальный DOM, обеспечивает высокую производительность даже при частых обновлениях интерфейса.
Концепция однонаправленного потока данных в React делает логику взаимодействия компонентов предсказуемой и легко отлаживаемой. Состояние приложения передаётся от родительских компонентов к дочерним через свойства (props), а для управления глобальным состоянием используется встроенный механизм Context API, позволяющий передавать данные через дерево компонентов без необходимости явной передачи на каждом уровне. В данном проекте Context API используется для распределения данных о настройках сайта, загружаемых с сервера один раз при старте приложения и доступных во всех компонентах без повторных сетевых запросов. Функциональные компоненты с хуками — современный подход к написанию компонентов React, пришедший на смену классовым компонентам, — обеспечивают более краткий и читаемый код, а хук useEffect позволяет управлять побочными эффектами, в том числе выполнять асинхронные запросы к API при монтировании компонента. Выбор React 19 обусловлен также тем, что данная версия библиотеки является актуальной и включает последние улучшения производительности и программного интерфейса.
Для организации навигации между страницами в одностраничном приложении использована библиотека React Router версии 7. Одностраничное приложение (Single Page Application, SPA) — это архитектурный подход, при котором весь HTML-код загружается однократно при первом обращении к сайту, а последующие переходы между страницами реализуются средствами JavaScript без полной перезагрузки страницы. Такой подход обеспечивает плавные переходы между разделами сайта, мгновенный отклик навигации и возможность реализации анимаций при смене страниц. React Router предоставляет декларативный API для описания структуры маршрутов приложения и компоненты для навигации — Link для обычных ссылок и useNavigate для программного перенаправления. Версия 7 данной библиотеки стабильна, хорошо документирована и является стандартным инструментом в экосистеме React-приложений.
В качестве среды выполнения серверной части приложения выбрана платформа Node.js. Данное решение позволяет использовать JavaScript как единый язык программирования для обеих частей системы — клиентской и серверной, — что сокращает контекстное переключение в процессе разработки и унифицирует инструментарий. Node.js основан на асинхронной, управляемой событиями модели выполнения, которая позволяет обрабатывать множество одновременных запросов без создания отдельного потока для каждого из них. Для небольшого корпоративного сайта с умеренной нагрузкой эта модель обеспечивает более чем достаточную производительность при низком потреблении ресурсов. Стандартная библиотека Node.js содержит встроенный модуль http, позволяющий создать HTTP-сервер без подключения внешних фреймворков, что и было реализовано в данном проекте. Отказ от использования Express или других фреймворков для Node.js является осознанным решением: он устраняет зависимость от третьих сторон и наглядно демонстрирует базовые механизмы работы HTTP-сервера, что имеет дополнительную дидактическую ценность в контексте учебного проекта.
HTTP-сервер на Node.js, реализованный в данном проекте, самостоятельно обрабатывает разбор URL и метода запроса, извлечение параметров, чтение тела запроса, управление сессиями через cookies и формирование ответов в формате JSON. Для аутентификации администратора используется механизм HTTP-сессий: при успешном входе создаётся уникальный идентификатор сессии, который сохраняется в памяти сервера и передаётся клиенту в виде cookie. При каждом последующем запросе к защищённым маршрутам сервер проверяет наличие действующей сессии. Хранение данных сессий в памяти процесса является достаточным решением для однопользовательской административной панели, не требующей масштабирования на несколько серверных экземпляров. В производственной среде данный подход обеспечивает приемлемую надёжность при условии периодического перезапуска процесса — поскольку вход в систему является простой операцией, повторная авторизация после перезапуска не представляет существенного неудобства.
В качестве механизма хранения данных для разрабатываемой системы используются JSON-файлы на файловой системе сервера. С точки зрения архитектурной модели данное решение функционально эквивалентно реляционной базе данных: для каждой сущности системы — заказов, элементов портфолио, услуг, данных команды, настроек сайта — существует отдельный файл хранилища, содержащий массив объектов с полями, соответствующими атрибутам таблицы. Операции чтения и записи выполняются средствами стандартных модулей Node.js для работы с файловой системой. Выбор JSON-файлов в качестве хранилища обусловлен рядом соображений. Данное решение не требует установки и настройки сервера базы данных, что упрощает развёртывание приложения и снижает требования к хостинговой инфраструктуре. В масштабах корпоративного сайта небольшой студии с несколькими десятками заказов и единицами одновременных пользователей производительность JSON-хранилища полностью достаточна — время чтения файла объёмом в несколько килобайт пренебрежимо мало. Кроме того, JSON-формат обеспечивает прозрачность и простоту резервного копирования данных: архивирование файлов хранилища средствами операционной системы даёт полную резервную копию всех данных. Для документирования логической структуры данных, применяемой в системе, разработана SQL-схема, описывающая соответствующие реляционные таблицы и связи между ними, — она представлена в разделе 1.5.
Для стилизации пользовательского интерфейса выбран подход на основе CSS-переменных без использования CSS-фреймворков или препроцессоров. CSS-переменные (Custom Properties) представляют собой стандартный механизм каскадных таблиц стилей, позволяющий определить именованные значения в корневом селекторе и использовать их по всему документу. Это обеспечивает единое управление дизайн-токенами — цветами, размерами шрифтов, отступами — из одного места, что соответствует принципу «единственного источника истины» и упрощает поддержку стилей. Отказ от CSS-фреймворков, таких как Bootstrap или Tailwind, обусловлен необходимостью реализовать нестандартную дизайн-концепцию: использование готового фреймворка предполагало бы преодоление его ограничений или переопределение большого количества стандартных стилей, тогда как написание CSS с нуля с использованием переменных даёт полный контроль над результатом без лишних накладных расходов.
Для типографики используются два шрифта, загружаемых с Google Fonts. Заголовки и крупные надписи оформляются шрифтом Syne — геометрической гротескной гарнитурой с характерным широким начертанием, хорошо подходящей для отображения крупного текста и создающей выраженный графический характер. Основной текст набирается шрифтом Inter — одной из наиболее высококачественных и читаемых гарнитур для экранного отображения, разработанной специально для пользовательских интерфейсов и оптимизированной для любых размеров. Сочетание этих двух шрифтов обеспечивает необходимый визуальный контраст между заголовочными элементами и основным текстом. Цветовая палитра системы строится на трёх базовых значениях: глубокий графитовый цвет #0C0C0E используется как основной фоновый тон, тёплый офф-вайт #F4EFE6 — как цвет основного текста и светлых фоновых блоков, лимонно-жёлтый акцент #E8F439 — для выделения интерактивных элементов, кнопок и ключевых акцентов. Эта палитра создаёт характерный современный вид, соответствующий эстетическим ожиданиям в отношении сайта творческой студии.
Инструментом сборки фронтенд-приложения служит Create React App — официальная утилита инициализации проектов React, предоставляющая готовую конфигурацию системы сборки на основе Webpack и Babel. Create React App обеспечивает сервер разработки с горячей перезагрузкой при изменении файлов, оптимизированную производственную сборку с минификацией и разделением кода, а также корректную настройку окружения без необходимости ручной конфигурации. В процессе сборки для производственного развёртывания Create React App генерирует директорию build, содержащую статические файлы оптимизированного приложения, которые затем раздаются Node.js-сервером. Для управления зависимостями проекта используется npm — стандартный пакетный менеджер Node.js, входящий в состав его дистрибутива.
Для управления версиями кода используется система контроля версий Git в совокупности с облачной платформой GitHub для хранения репозитория. Git обеспечивает полную историю изменений кодовой базы, возможность отката к любой предыдущей версии и безопасное сохранение результатов работы. GitHub дополнительно служит платформой для непрерывной интеграции с сервисом развёртывания. Для публичного развёртывания приложения выбрана облачная платформа Render, предоставляющая услугу хостинга Node.js-приложений с автоматическим развёртыванием при каждом обновлении ветки репозитория на GitHub. Render поддерживает конфигурирование сервиса через файл render.yaml, что обеспечивает декларативное описание параметров развёртывания и воспроизводимость окружения. Более подробно процесс развёртывания описан во второй главе работы.
Таким образом, технологический стек разрабатываемой системы включает React 19 с React Router 7 для клиентской части, Node.js на встроенном HTTP-сервере для серверной части, JSON-файлы в качестве хранилища данных, CSS-переменные для стилизации, Create React App как инструмент сборки, а также Git, GitHub и Render для управления версиями и развёртывания. Выбор каждого из этих инструментов обоснован с учётом требований к системе, описанных в предыдущем разделе, и обеспечивает необходимый баланс между функциональными возможностями, удобством разработки и простотой эксплуатации. Следующим этапом является проектирование структуры базы данных, описанное в разделе 1.5.
